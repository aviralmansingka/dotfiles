## 1. The write path

- A commit is one atomic unit of every record kind. `conversation.commit(tx => …)` may append
  entries, create or retire documents, create tasks, admit submissions, and settle them
  together; all is stored or none is (spec §1 inv. 1, §4).
- `src/storage/store/commit.ts:73-75` — `class DurableCommit implements SeriesCommit,
  StagedWrite { readonly order = "write"; readonly writes: readonly StagedWrite[] }`. A commit
  is its write list; `:110 check(step)` runs Durable's own refusals and writes nothing;
  `:152 apply(step)` returns the writes.
- `src/session/transaction.ts:811 settleSuccess()` — "Seal after callback success, prepare
  every open change, and assemble the atomic batch. Any failure aborts every change before
  Storage admission." `:800 settleFailure()` aborts all; `:947 adopt(seq)` applies to memory
  only after storage succeeded.
- **Decisive line**, `src/session/session.ts:199-202`: "Only committed state is observable. A
  deferred commit (`CommitPersistence`) is committed in memory first: it is adopted and shown
  to the Session's own observers, and its changes wait … for the first commit that reads or
  writes the document, the document's deadline, a drop of its tracker, or close."
- `src/session/session.ts:204-211`: every job read touches its key, and while an unpublished
  commit writes that key the job waits for publication, "so no job observes state that is not
  stored".
- Spec §4: a commit is published after the storage call settled. Order: caches, telemetry, own
  observers (views, waits, scheduler), then `observeCommits()` one microtask later.
- The boundary is Storage admission, not the callback. A stored prefix publishes; later
  batches are refused or fail. Publication, never the store, moves memory.

## 2. Checkpoints and the five documents

- A checkpoint is the whole execution state of one task (spec §5.1, §5.2 "effect sandwich":
  commit intent → external effect → commit outcome or next phase).
- A phase must return a changed checkpoint, a wait, a sleep, or an outcome. Otherwise it faults
  (`src/harness/scheduler.ts:2246-2253`).
- "There is no sleep inside a phase: a phase reruns from its top after a crash or close"
  (spec §5.6). Work after a wait belongs in the next phase, with its inputs in the checkpoint.

| document | keeps durable |
|---|---|
| `pi.live` | run control, generation attempt, committed partial, retry backoff, deferred poll, tool slots, nested slots, compactions, `runFailure`, `compactionFailure` |
| `pi.inbox` | queued submissions (steer, followUp, write) in ID order |
| `pi.usage` | spend per provider/model and per tool |
| `pi.agent` | model, thinking level, extensions, tools, instructions, cwd, maxTurns — by name |
| `pi.provider` | per-conversation UUIDv7 `sessionId`; survives reopen, retry, reset, compaction, model change; fresh for a fork |

## 3. Resume, verified in source

1. `Harness.open` = construct + `openTasks()` (`src/harness/harness.ts:610-630`, `:316-318`).
2. `scheduler.open()` (`:483-517`) scans all five live statuses (`:81` = pending, running,
   waiting, sleeping, completing) and, in the commit that opens, writes `running` → `pending`
   with `restarts = (restarts ?? 0) + 1` (`:508-511`), then schedules a reconcile pass.
3. `resume()` (`:529-534`) only enables scheduling, marks due sleeps runnable, and kicks.
   `#planReservation` (`:2117-2125`) drops tasks with a live invocation, `completing`,
   waiting, or asleep; the rest are reserved in one commit and started.
4. A task cut off at or past `restartLimit` is faulted at reservation (`:2019-2028`) for
   extension kinds and abort handlers; built-in kinds end themselves.

**Correction to README:127** ("Work interrupted by a crash or close stays pending"): after a
crash the record still says `running`; `open` writes it back to `pending` and counts. A close
writes `pending` directly with no count (`scheduler.join()` → `writeAtClose`, `:390-397`;
spec §5.4 "A close is not a crash"). So `open` reconciles, and `resume()` starts the scheduler.

- `resume()`: idempotent, throws after close, `ReadOnlySession` on a read-only Harness.
  Submitting or waiting also enables scheduling.
- `readOnly: true`: loads live tasks as committed, reconciles nothing, rejects every write
  before Storage, `wake()` is inactive, `onWake` never runs, no restart is counted. JSONL
  storage must also open `{readOnly: true}`.
- `requestId` dedup happens before any write; a known ID returns the existing submission with
  no write.
- Retry policy: `{enabled: true, maxRetries: 3, baseDelayMs: 2000, maxAgentDelayMs: 60000}`
  (`src/harness/agent.ts:23-28`).
- **Correction to the orchestrator's assumption:** `TaskOutcome.status` is `completed | failed |
  aborted | orphaned | faulted`. There is no `task_failed` and no `task_orphaned` report kind.
  `onReport` kinds are `storage_failed`, `task_faulted` (`reason: "threw" | "restart_limit"`),
  `task_interrupted` (`reason: "restart_limit" | "interrupted"` with `restarts`),
  `migration_failed`, `task_outdated`, `task_error`, `extension_error`, `host_error`,
  `listener_error`. `restart_limit` is a reason and diagnostic code, not an outcome.

### Crash-resume walk-through

1. `submit({type:"input", requestId:"r-1"})` → one commit: submission record plus `pi.user`
   entry (idle) or `pi.inbox` item (busy).
2. Reservation commit: task `pending → running` at `{phase:"prepare", attempt:1}`; `prepare`
   commits `{phase:"request", …}`; the model streams.
3. Partial answers commit as deferred writes into `pi.live.generation.message` every ≤100 ms;
   storage gets them at the next commit that reads `pi.live`, or within ≤1000 ms.
4. **Process dies.** Storage holds the submission, the entry, the task `running` at `request`,
   and possibly a partial.
5. `Harness.open` → `scheduler.open` writes `pending` with `restarts = 1`; `wake()` reports
   active.
6. `resume()` → reserve → the `request` handler sees `task.restarts !== undefined` and treats
   it as a failed attempt, not a resend (`src/harness/generation.ts:126-127`). It commits the
   stored partial as an aborted entry and either sleeps until the retry backoff
   (`pi.live.generation.retry`) or ends the run `unanswered` with `runFailure.reason =
   "interrupted"` (`:391-437`).
7. After the backoff, `retry` → `prepare(attempt + 1)` → a new request.
8. **Runs again:** the interrupted generation phase only. **Does not run again:** the
   submission, the committed entry, a tool task that committed its result, a task parked at
   `parked` (no tool code runs), and a parked call's children.
9. Each crash increments `restarts` unless the task committed a differing state. At 5 the run
   ends `restart_limit` and `onReport` gets `task_interrupted`.

## 4. The crash window

- README:628: partial answers and tool output are committed at most every 100 ms; storage gets
  them at the next commit that reads `pi.live` and at the latest after
  `settings.progress.persistWithinMs` (default 1000 ms).
- Spec §4.1: "What a crash loses is a held commit's changes: up to `withinMs` plus the line and
  I/O delay. A value read outside a commit (`snapshot()`, a watch) may be ahead of Storage;
  nothing durable may be derived from it without reading it in a commit."
- Defaults in source: `partialIntervalMs 100`, `outputIntervalMs 100`, `persistWithinMs 1000`
  (`src/harness/agent.ts:37-41`). `Infinity` stores only at the next read/write or close.
- Only two commit kinds are ever deferred: generation partials and running tool progress.
- Exception, spec §8.2: "a stream that crashes before its first store leaves no aborted entry,
  and that attempt's usage is not recorded."
- Durable but unpublished parts are recovered on reopen; they are unseen, not lost.
- Backend retention: SQLite `synchronous = NORMAL` may lose the newest commit on power loss.

## 5. Sleeping, waking, signals

- A task parks by committing a state that ends the invocation: `sleeping {checkpoint, until?,
  signals?}` or `waiting {checkpoint, on, policy}`.
- A sleep holds no process, survives reopens, and resumes at its checkpoint when the clock
  reaches `until` or a signal key holds an unconsumed value.
- The wake writes `task.state.wake` (`time | expired | signal | tasks`). One wait per key.
- Concrete park: `execute()` returns `{kind:"sleep", checkpoint:{buildId},
  signals:[CiResult.key("done")], until: now + 2h}`. One commit stores the checkpoint, sets the
  slot `sleeping`, and ends the invocation. A webhook calls `harness.signal(taskId, CiResult,
  "done", {…})`, which wakes it. On wake the handler calls `execute()` again, reads
  `api.readSignal`, and checks `api.memo("ci.run", …)` before the external effect.
- Without `onWake` one timer keeps a Node process alive. With `onWake` the Harness arms no
  timer and reports `{active, at}` so a Durable Object alarm can call `resume()`.

## 6. Replay safety

- A tool call is its own `pi.tool` task: `call → execute{arguments, replay, wake?,
  checkpoint?} → parked`. Intent is committed before `execute()` runs
  (`src/harness/tool.ts:104`).
- `src/harness/tool.ts:142`: a rerun happens only when `replay === "safe"` in both the stored
  intent and the current policy.
- Otherwise the tool gets an `interrupted` error result built from its durable partial output,
  and the task ends `failed` (`:164-168`). `replay` defaults to `"unsafe"`.
- A tool must therefore accept a second `execute()` with the same arguments, and it must
  memoize an idempotency key before acting.
- A nested call with the same key reattaches to its existing task and returns its result
  instead of starting again: at-most-once dispatch, not exactly-once execution.
- A restart while parked runs no tool code at all, even for an unsafe tool.

## 7. `docs/group-commit.md`

It shows that batching does not weaken durability. Each logical commit keeps its own `seq` and
its own publication, but commits admitted while one write is in flight travel as one
`Storage.commit(batches, receive)` call, each batch atomic and checked against earlier batches.
`receive` is a receipt, not publication, so a callback cannot observe unstored state. On a
failure the stored prefix survives and publishes, and reopening recovers the rest.

## 8. What durability does not cover

- External effects: no exactly-once side effects. A crash inside a phase re-runs the phase, a
  tool is re-entered or reported interrupted, and a request already sent to a provider was
  billed.
- The deferred window, plus a stream that crashed before its first store.
- Anything derived outside a commit (`snapshot()`, a watch value).
- Backend retention: SQLite `synchronous = NORMAL`, JSONL fsync, memory stores nothing. One
  writer at a time, no cross-process lock.
- Liveness: a task whose definition is missing or too old stays blocked and live forever; only
  a registry change or an abort moves it. A missing alarm strands a sleep.
- Non-cooperative code: no forced termination; a hung phase delays `closed`.
- Explicit non-goals (spec §13): no whole-Session DOM, no independent event journal (why
  `watchEvents()` was removed), no CRDT or offline multi-writer, no automatic checkpoint
  heuristic, no JSONL compaction.
