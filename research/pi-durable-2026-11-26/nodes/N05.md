# N05 brief — Transport and hosting layer

Child: n05-transport-durable. State: done. Evidence: absence greps over the local 1.6.1
tarball, chord 1.6.1 tarball (`/tmp/n05chord`), `pi-protocol`/`pi-client` 1.1.0 tarballs,
pi-coding-agent 1.6.0 docs, `apps/p2` source, and five public dependents.

## Answer

**No.** pi-durable 1.6.1 ships no wire protocol, no server, no HTTP/RPC/socket surface, and no
serialization format for views or ops. It is an in-process object library that ends at
`(value: ConversationView, ops: Op[])` handed to the host's own async callback.

## 2. The host is an in-process object

- README Concepts: "Harness: one open storage plus the machinery that runs agents on it."
- Quick Start is all in-process: `Harness.open(new MemoryStorage(), {models, registry}, context)`
  … `harness.close(context)`.
- The only client-facing seam is a callback the app owns (README ~590): `watch.start(async
  (call) => { … render(value); await send(ops); // for example to a remote client that applies
  them })`. `send` is the host's own function.
- Storage: "One process writes a storage at a time; there is no cross-process locking." The one
  "remote" concession is latency tuning for a remote *backend* (`settings.progress`), not a
  remote UI.
- Examples 18-json, 35-durable-on-the-store, 36-durable-views, 37-harness-registry show the
  intended composition: compose pi-durable into a chord host; pi-durable supplies none of it.

## 3. What chord supplies (the decisive question)

chord 1.6.1 has 27 subpaths; the transport-relevant ones:

| Subpath | What it is |
|---|---|
| root | contracts (`local`, `remote`, `method`), `createHost`, documents, derives, jobs, **links** (`memoryLinkPair`, `ipcLink`, `webSocketLink`), registries, store |
| `chord/http` | Web-standard `fetch` handler (`createHttp`), authenticators, security baseline, Node listener, `nodeRequest`, **the links endpoint** |
| `chord/workers` | one forked worker per address of a host kind, on demand |
| `chord/surfaces` | server side of client surfaces: `webSurface` (base bundle, plugin scripts, the page), `tuiSurface` |
| `chord/web` | browser side: `startPage` |
| `chord/react` | `HostProvider`, `useHold`, `useWatch`, `useRefState`, `useVariant`, `useRegistry`, `usePageState`, `watchStore` |
| `chord/app` | `startServer`, `startWorker`, sessions, owner sign-in, device pairing, files |

Peer deps: `ws@^8.21.0`, `react@^19.3.0`, `esbuild@^0.28.2`. The npm description ("HTTP,
workers, web and terminal clients") is accurate.

- The documented bridge is `self.follow(attach)`, whose chord doc comment names Durable's
  views: "A source following another runtime's synchronous observer (Durable's views…)".
- What crosses a chord link is chord's format, not pi-durable's: one `state` message per commit
  per link and origin, `binaryCodec` by default or `textCodec` for JSON tuples.
- chord supplies no pi-durable components. Clients hold the app's contracts; agent code cannot
  address clients (`docs/design.md` §24).

## 4. The reference host `apps/p2` — hand-written, unpublished

- `"private": true`, version 0.0.3, npm 404.
- `src/hosts/server.ts` builds `node:http` `createServer` + `ws` `WebSocketServer({noServer:
  true, maxPayload: MAX_CLIENT_FRAME, perMessageDeflate: false})` and calls
  `host.accept(webSocketLink(limitedSocket(socket)), {principal, limits:{part:
  MAX_CLIENT_FRAME}}, BACKGROUND_CONTEXT)`; it also writes its own upgrade authorization and a
  `Upgrades` registry for plugin sockets. It does **not** use chord's `createHttp`.
- Browser side uses chord's `webSurface(...)` + `startPage({connect: () => new WebSocket(url)})`.
- View path: `self.follow((observer, ctx) => harness().durable.observeConversation(id, observer,
  ctx))` → `deriveTyped` → a second per-client derive that turns image parts into references →
  a `local` contract member `view: ViewSchema` and a `remote` contract `Chat` with `viewer` and
  `participant` variants → chord replicates with its own ops.
- So p2 wrote: an HTTP server, a WS server, per-upgrade auth, a local/remote contract pair with
  variants, derives that reshape the view, and a React client with its own connection store.

## 5. `pi-protocol` / `pi-client` 1.1.0 do not target pi-durable

- Deps: `pi-protocol` = `typebox` + `chord@^1.1.0`; `pi-client` = `chord` + `pi-protocol`.
  Neither depends on `pi-durable`.
- Frames: 4-byte big-endian length + one definite-length CBOR item; protocol version 8; a
  `serverId` handshake; targets `{serverId}` or `{serverId, sessionId, attachmentId}`.
- Payloads are chord's: `{serviceId, instance?, member, args}` calls, `$chord.service` control,
  catalogues, subscription snapshots. "The durable Session and its Harness remain local to the
  Session worker process."
- `pi-protocol` exports `./cbor`, `./codec`, `./framing` and envelope types — **no server, no
  listener, no host adapter**. "Server and worker lifecycle is intentionally outside this public
  protocol."

## 6. Pi's own RPC is a different protocol and unavailable here

- pi RPC = "JSON records on stdin and stdout", strict JSONL framing, four record families:
  stdin `Command`, stdout `response`, stdout session event, extension UI record.
- Events are fact-shaped and streaming: `agent_start`, `turn_start`, `message_start`,
  `message_update` (`text_delta` with `contentIndex`/`delta`), `message_end`, `turn_end`,
  `agent_end`, `agent_settled`, plus tool/queue/compaction/retry events.
- pi-durable has no equivalent by design, and neither package depends on the other. A
  pi-durable app cannot reuse pi's RPC: the envelope carries the coding agent's session
  format, with no `ConversationView`, documents, or commits.

Two independent reimplementations of the same seam: pi-durable-cloudflare forwards `call.ops`
verbatim in JSON and re-applies with `applyImmutable`; pi-pocket sends coalesced view changes
every 90 ms. Each picked its own framing, reconnect, and authorization story.

## 8. The exact gap for a remote-UI author

1. A server process and a byte transport. pi-durable has no listener; chord has one, but
   pi-durable does not surface it and no published example exercises chord's path.
2. A wire contract: names, subscribe/unsubscribe semantics, what a window means to a client.
3. A serialization decision: send chord `Op[]` and require the client to import `chord/delta`
   (pi-durable-cloudflare), invent a version scheme (`?known=`), or adopt chord `bound`/`state`
   (p2).
4. Command routing back: `submit`/`stop`/`configure`/`entries` paging, and who may do them.
5. The UI itself. chord gives `startPage`/`useWatch` and a bundle builder, but components that
   render `entries`, tool slots, streaming partials, and `runFailure` exist in no published
   package.
