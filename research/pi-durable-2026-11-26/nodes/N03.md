## 2. Size of the `Storage` contract

`dist/types.d.ts:1175-1242`: **18 members, 17 required** — `commit(batches, receive, context)`,
optional `publishing(publish, context)`, `mintId()`, `conversation(id)`,
`scanConversations(query, limit, cursor)`, `entry(id)` / `entry(conversationId, id)`,
`findLatestHeadMarker()`, `scanEntries()`, `task(id)`, `scanTasks()`, `submission(id)`,
`scanSubmissions()`, `submissionByRequest(conversationId, requestId)`,
`findDocument(address, at)`, `document(id, at)`, `scanDocuments()`, `close()`.
Five record types plus document revisions, each a frozen JSON record.

Invariants:
- One `commit()` call = one backend transaction; each batch is one atomic commit with its own
  `seq`, checked against the state the earlier batches left. SQLite uses no savepoints,
  because Durable Objects do not allow them.
- `mintId()` returns IDs above every minted and every stored ID, across reopen; ID 1 is
  reserved for the root conversation.
- `receive(index, seq)` runs once per durable batch, in order, synchronously, after all
  batches are durable and before the next commit starts. It is a durability receipt, not
  publication; it calls no Storage method and never throws.
- Partial refusal stops at the first batch Durable refuses; earlier batches stay durable.
  Result is `CommitResult = {kind:"stored",stored} | {kind:"refused",stored,refused}`.
- A thrown `commit()`/`mintId()` error is fatal to the Session; reads may fail alone with
  `StorageRequestError`.
- Reference implementations are **760–1,211 lines** each. A relational backend also needs the
  9-table/16-index schema (`dist/storage/sqlite/schema.js`) and a document base/delta model
  with fork ancestry. Chord's `SqliteDatabase` facade has 7 members (`exec`, `run`,
  `runCounted`, `get`, `all`, `transaction`, `close`); README 1053 lists six and omits
  `runCounted` (added in 1.5).

## 3. Conformance is real and sized

`./testing` ships `createStorageConformance` + `registerStorageConformance` (Vitest/Jest
`{describe, expect, it}`), `createEnvConformance` + `registerEnvConformance`,
`commitWrites()`, `createExpectAssertions()`, and a benchmark kit (`STORAGE_MEMORY_SCALES`,
`TIMING_SCALE`, `seedStorageBenchmark`, read/write benchmark tables).

- **33 storage cases**: root ID 1 reservation, receipt semantics ("receives a durable commit
  once before resolving, and never a refused one"), atomic rollback of mixed writes,
  detachment, prototype-like JSON keys, out-of-order entry indexing, cursor continuation,
  both scan orders, deep fork-history traversal, task/submission/document lifecycles,
  "keeps one global record ID namespace and rejects exhausted ID minting", partial-batch
  refusal, "rejects every operation after close".
- **21 env cases**, 15 mandatory and 6 gated by options (`listFiles`, `symlinks`).
- The gscode1 fork registers the suite in three lines, with a per-test schema.
- Reading: backend authorship is supported by design — a contract, a 33-case gate, and
  benchmarks. "Supported" means "you can write one", not "one exists".

## 6. `ExecutionEnv` is the app's job

- `ExecutionEnv extends FileSystem, Shell` (`dist/env/index.d.ts`): **27 required members + 1
  optional** — `id`, `cwd`, `absolutePath`, `joinPath`, `readTextFile`, `openTextLineReader`,
  `readTextLines`, `readBinaryFile`, `openBinaryReader`, `writeFile`, `appendFile`,
  `truncateFile`, `flushFile`, `renameFile`, `fileInfo`, `listDir`, `listFiles?`,
  `openDirReader`, `watch`, `canonicalPath`, `exists`, `createDir`, `remove`, `createTempDir`,
  `createTempFile`, `cleanup`, plus `Shell.exec(string | argv[], options, ctx)` with streaming
  `onOutput`, spill thresholds, and a bounded `window`, and `Shell.cleanup`.
- Results are `Result<T, FileError>`; the API does not throw for expected failures.
- Only `NodeExecutionEnv` ships (`dist/env/node.js`). It does not implement `listFiles`;
  README 558 names `pi-env`'s `RemoteExecutionEnv` and `LocalExecutionEnv` for that.
  `@earendil-works/pi-env@1.6.1` is a **separate package** (208,938 downloads/month), with
  `RemoteExecutionEnv implements ExecutionEnv` and `LocalExecutionEnv extends
  NodeExecutionEnv`. No workspaces abstraction ships in pi-durable.
- `HarnessOptions.env?: (target: EnvTarget, context) => ExecutionEnv | undefined`, called per
  tool call, per section render, and by `runtime.env()`. "Without an environment, the built-in
  tools fail with an error result" (README ~545).
- Consequence: in a browser or a Worker, tools do not run at all until someone writes the
  27-method environment. Third parties do exactly this (`pi-env`,
  `@flydotio/pi-durable-sprites`, `pi-durable-expo-env`).

## 7. Migration and compatibility statements

- SQLite: `SQLITE_MIGRATIONS` has v1 (9 tables, 16 indexes) and v2 (tasks rebuilt for the
  `sleeping` status); `CURRENT_SQLITE_SCHEMA_VERSION` is the last migration (2). Migrations
  run automatically at open (`dist/storage/sqlite/storage.js:72`), tracked in
  `durable_schema`. Identifiers are immutable by contract.
- CHANGELOG 263: "A migrated database cannot be opened by 1.3.0 or earlier, so a deployment
  cannot roll back past this release. JSONL storage needs no migration."
- 1.6.0: a database written by it "is not meant to be opened by an older Harness"
  (`pi.tool` v4, `pi.generation` v3 → `task_too_old`).
- IndexedDB: `DATABASE_VERSION = 1`; `upgradeneeded` creates objects only when
  `oldVersion === 0` — **no upgrade path exists yet**.
- Changing the storage prefix does not migrate data.
