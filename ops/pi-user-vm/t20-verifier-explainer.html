Multi-VM GPU Host · T20

Three proofs. One tested VM choice.

The evidence moves from architecture choice to a working guest, then proves that the guest survives a real cold lifecycle. Each verifier answers one question and deliberately leaves downstream policy alone.

$ verify T20 --ordered V01 → V02 → V03 [PASS]
V01

Which libvirt machine type should user VMs use?

● PASS

What it proves

Three candidates receive a real disposition. Q35 and microvm both booted Ubuntu and passed storage, networking, console, and lifecycle probes. Q35 wins because it uses the ordinary supported path; Cloud Hypervisor cannot be managed by this host's installed libvirt build.

What it does not decide

  • Production image lifecycle
  • VM resources or restart policy
  • Credentials or user migration
V02

Does the selected guest have the minimum usable boundary?

● PASS

What it proves

The approved Q35 identity appears in live domain XML, and the guest is usable for a Pi-style workload: virtualization is real, user services work, home is writable, and TCP crosses the tested libvirt bridge path. Strict SSH key and host-key checks were used. The listener is temporary and removed after each observation.

What it does not decide

  • Tailscale state was not inspected or altered.
  • No Tailscale enrollment was performed.
  • No exit node was required.
  • Public routing was not evaluated.
V03

Does guest state survive a real libvirt cold lifecycle?

● PASS

What it proves

The marker is durable, not merely cached in a running guest. Libvirt reaches shut off, starts the same persistent domain, SSH recovers, and the exact marker plus user service behavior survive the boundary.

Still outside T20

  • Crash-restart and autostart policy
  • Production backups and image recovery
  • Long-running Pi process migration
