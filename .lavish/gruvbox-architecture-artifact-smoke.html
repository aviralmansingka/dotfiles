Target behavior · one command · three owners

A command crosses boundaries. Its concerns do not.

The CLI adapter translates process input, the domain service applies policy, and the storage backend persists state. Success and failure return through the same boundaries, with each owner translating only its own vocabulary.

Three owners, one direction of dependency

Interface → policy → persistence

The domain contract is the seam; terminal and driver details stay outside it.

CLI adapter · interface

Translate process input

Parse argv, validate command shape, create a typed request, render the final response, and choose the exit code.

Domain service · authority

Decide what the command means

Enforce invariants, authorize the use case, orchestrate dependencies, and return a domain outcome.

Storage backend · durable state

Perform persistence

Serialize data, execute the read or write, protect durability, and report backend failure without printing or exiting.

How does the command travel?

The failure return path

A failure is data moving outward, not an exception escaping upward.

Diagnostic detail may be logged; public vocabulary stays stable.

01 · REPORT

Backend names the operation

Return StorageFailure(kind, operation). Do not print, terminate, or choose a user message.

02 · INTERPRET

Service applies policy

Map storage vocabulary to CommandFailure(code, context) and decide whether retry is valid.

03 · PRESENT

Adapter communicates

Map the domain failure to one concise stderr message and a documented non-zero exit code.

04 · RETURN

Shell observes the result

The caller gets a stable process contract; backend exceptions and persistence details remain contained.

Given a storage write failure, the shell receives one actionable message and a non-zero exit code—without storage details crossing the CLI boundary.
