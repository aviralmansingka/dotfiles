BOUNDARY SUMMARY
Draw the boundary around the single `machine-manager` Deployment pod: one Go binary that owns four listeners (private gRPC 50053, public gRPC 50054, boot HTTP 8080, web 8082 plus River UI 8081), runs its River workers in-process, ships its Svelte UI and its `machine-audit` binary embedded, and owns the `machinemanager` Postgres schema including the `river_job` queue. Everything it reaches over the wire is a neighbour — the Python instance-manager client in modal-eks-cluster, the host-resident machine-agent/s3-boot/hostbench/audit execution, vendor provider and BMC APIs, `machine-janitor`, AWS Secrets Manager/S3, and the Gateway/NLBs. I rejected three tempting counter-examples: `machine-agent` (same Go module, same `providers` package, but a different binary that runs on the host), `machine-audit` (embedded *in* the image, but its whole purpose is to execute on the host), and `machine-janitor` (same k8s namespace and the same S3/IAM family, but its own image, chart and deployment).

CONFIDENT vs UNCERTAIN
- **Postgres: inside (schema) / outside (instance).** Claim for inside: `main.go:118` runs `migrations.RunMigrations` at startup, and every table in `migrations/*.up.sql` is the component's own. Claim for outside: the RDS instance, parameter group, password and secret are created by an unrelated Pulumi stack (`ops/pulumi/machine-manager/resources/database.py`), so a C4 "container" reading gets a store it did not provision. I resolved it as "own schema, borrowed instance" and flagged it per store rather than silently picking one.
- **`machine-audit` binary.** Inside by packaging (embedded via `//go:embed`, i.e. it is *in the image*), outside by runtime (it executes on the machine over SSH). Rule 5 of the brief points to outside; the "ships with the component" default points to inside. I listed it inside but labelled the runtime unit "shipped payload" so the drawing can annotate rather than misplace it.
- **`providers` / `bmc` adapters.** Could be drawn as separate components at L3 (they are packages with clear interfaces — `providers.Registry`, `bmc.AccessResolver`) but they are linked into the one binary and share its lifecycle, so they stay inside at L2.
- **River queue tables.** `river_job` is created by River's own migrator (`README.md:14-15`), not by `migrations/`, yet the component adds its own index (`000021_river_job_metadata_gin_index.up.sql:1`). Membership is defensible either way; I called the queue inside because the database it lives in is the component's and no other service consumes it.
- **`cluster-manager`.** It creates and resizes gcore GPU clusters — plausible to draw as a distinct container, but it is `go/machine-manager/cluster-manager` linked into the same binary and driven only by a goroutine at `main.go:308`.
