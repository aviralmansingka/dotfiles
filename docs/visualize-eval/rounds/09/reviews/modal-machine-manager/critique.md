## Source comparison and coverage

The fixed source explicitly requires **all 17 components and all 23 directed relations** across views; the historical generated diagram is evidence of those enumerated relationships, not independent verification of real-world architecture. The shipped specs declare 16 components and 20 relations. The missing node is `web` (humans + mmctl), and missing relations are `web → wapi` (HTTP), `pgrpc → db` (machine rows), and `pub → db` (machine state). Those are critical semantic defects under the frozen case, not merely a weak coverage score or an excused yield. The per-edge audit in `reviewer-result.json` covers all 23 required relationships with source refs, the observed direction, label/endpoint state, relevant image regions, and failure IDs. There are no additional drawn relations in the four final specs beyond those 20; no apparent bridge or junction is a distinct extra link.

V1 visibly preserves the straight enqueue → provision → allocate chain. V2 declares the iPXE request and `boot.ipxe + S3 args` response as two independent, oppositely directed routes in one view, but the 77×47 capture clips the boot server and one arrowhead; the machine-agent and S3 destinations are below the target viewport, and the palette partially covers `runs on host`. Thus the intended co-viewed handshake cannot be fully read as captured. As a result the requested enqueue → provision → allocate → iPXE → image pull → heartbeat → state-write order is not explicitly readable in one direction across the views. The v3 `audit / reimage` label drops `verify` from `audit / verify reimage`, and its placement may be confused with the adjacent agent route. V4's queue → janitor → webapi → queue cycle is traceable after following its long right-side return; SSH → machines remains separate.

At 82×51 v3 `audit / reimage` [19,25,15,1] and `cluster state` [41,26,13,1] lie near neighboring routes. V4's `reinstall/reprovision` [44,10,21,1] is away from its relevant outgoing path and near a competing branch. The checker reports zero ambiguous owners, but the human-visible placement is uncertain; recorded failed layouts do not prove that an unambiguous placement was impossible. ## Family classification and recipe

`generation.json`, `step0_classification`, states `family: lifecycle-machines` and this exact evidence text:

> one queue node fans to five phase targets (River jobs -> registry, SSH/BMC ops, janitor, S3, Postgres) while the machine side advances in a fixed stage order (enqueue -> provision -> allocate -> iPXE boot -> image pull -> agent heartbeat -> state write), and the chat's final correction is 'one dot alive per line', i.e. one live dot per transition.

The source supports this dominant family: five independent queue targets, an ordered provisioning/boot/heartbeat/state story and the final sparse-dot correction. The same section states a secondary service-mesh recipe for machines ↔ boot server. Two distinct edges and labels are declared in v2, but not both complete with their arrowheads in the target capture. The lifecycle recipe is likewise incomplete in the captures. A stated recipe yield identifies routing and height limitations but does not establish that every phase-preserving and complete design is impossible: it documents a finite three-candidate budget for each view. Even a properly evidenced recipe yield would not excuse missing required relations, source fidelity, or fit failures.
