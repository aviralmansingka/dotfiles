All 23 directed endpoint pairs are drawn, including machine → boot server `iPXE request` and boot server → machine `boot.ipxe + S3 args` as distinct, oppositely directed arrows in v2. The exact S3-args response is present, not replaced by an S3-only request. River jobs → S3 diagnostics is distinct from machine image retrieval and from the janitor branch. Janitor → webapi proposals are present. The JSON audit assigns **21 pass, 2 fail**: e19 and e22 fail because their action labels have ambiguous owners, even though their endpoint strokes can be followed.

The v1 provisioning chain reads top-to-bottom from control plane to machines. In v2, the boot request runs **up** to the boot server and the response runs **down** to machines; the machine-agent heartbeat proceeds downward to public gRPC and Postgres. Thus the logical source sequence can be reconstructed across views and by following arrowheads, but it is not a literal single page-direction progression across the boot exchange. Ops and reconcile are side views. This matters as a deviation, not as an automatic category-fit failure under round 11.

The generator's classification in `generation.json`, `step0_classification`, is verbatim:

> family: lifecycle-machines
>
> evidence: one machine-manager lifecycle reads in a single phase order (control plane -> private gRPC -> River jobs -> provider registry -> bare-metal providers -> bare-metal machines -> iPXE boot -> machine-agent heartbeat -> Postgres) and the widest fan in the source is five out of one node (River jobs -> reg/db/ssh/s3/jan), with the source asking for one slow dot per live line.

The recorded six-node measurements demonstrate pressure on 77×47; they do **not** independently establish the stronger assertion that every possible ten-rank arrangement is impossible. Under the softened criterion a named, source-backed family and recorded reasons for the deviations suffice; no additional impossibility proof is imposed on this family decision. ## Defects and evidence gaps

1. **Renderer motion defect, high — e1/e5/e7.** In `pinned/v1-77x47.txt`, using (row,column), frame 0–3 dots are `(7,39),(7,39),(8,39),(8,39)` for e1; `(23,38),(23,38),(24,38),(24,38)` for e5; and `(39,38),(39,38),(40,38),(40,38)` for e7. Each repeats these cells through frame 47 instead of traversing the drawn bends to its target. The checker nevertheless says zero violations. The generator's coordinate convention is zero-based; the above measurements are 1-based. Independent comparison also corrects its v2 claim: the boot-pair dots visit **three** route cells and wrap, e.g. downward dot `(11,40) → (12,40) → (13,40) → (11,40)` at frames 0, 2, 4, 6. They are not confined to two cells like v1. Unequal arrival times are not a defect: constant speed, not same-arrival, is the rule.
2. **Motion choice defect, medium — e3/e6.** Historical animated source specifies `enqueue job` and `provider API` as live edges; the later human correction asks for one live dot per line. The candidate treats both as static handoffs. The separate machine-agent `runs on host` residency edge is appropriately static. Even apart from this choice, the measured oscillation independently fails animation.
3. **Label-owner defects, high — e19/e22.** In v3 `diagnostic events` at `[23,24,17,1]` ends adjacent to the S3 branch although the intended left branch ends at janitor. Three recorded v3 attempts all retain an ambiguity warning, but changing target count and order three times does not prove no possible unambiguous placement. In v4 `gcore sync, 1 min` at `[41,17,17,1]` sits by the other reconcile output, making provider-sync versus cluster-state ownership uncertain. The generator records both tradeoffs; this is not a demonstrated impossibility exception.
4. **Group-order defect, medium.** In v3 `janitor app` is left of `SSH + BMC ops` (nodes at `[17,26,11,1]` and `[53,26,13,1]`), contradicting the generator's explicit `ops: ssh, jan, slack` order and the source's SSH-then-janitor listing. Hue family correctness and the absence of region boxes do not correct the order.
5. **Frozen-provenance evidence defect, high.** `metadata.json` states `cases_sha256` `e69179e59a3d36985cd7e8692b319b566701f88caef385c9cbde76d060c92d05`, but `shasum -a 256 docs/visualize-eval/cases.json` produces `e69179e59a3d36985cd7e8692b319b566701f88caef385c9cbde76d060c92d05`. The case's own source, expected, and historical-variants files independently match metadata, as do the skill, rubric, and executed renderer. The result reports the **actual** dataset hash; provenance remains unresolved rather than silently accepting the metadata value.
6. **Full-lap evidence gap, high.** Each target dump contains 48 frames at 100 ms intervals, but in v4 the janitor → webapi dot has progressed only from `(14,20)` in frame 0 to `(16,44)` in frame 47; the route continues toward the webapi arrowhead. It has not completed a lap in this capture. The in-pane frame sequences are shorter. Target-size fit is independently proven, but full-cycle motion evidence is not. A known animation failure remains a failure, not merely a blocked category.
7. **Crossings and chrome observations.** V4 has three visible `⌒` bridges (two where the janitor route crosses reconcile outputs and one where the webapi-to-jobs route crosses the state route) and three checker-reported touching bends. They are distinguishable from junctions. Rejected v4 variants alter labels and edges as well as crossing count, so they do not prove all three avoidable. At target size, the v4 UI title truncates; this is not a truncated graph label and is not a fit defect.
